二、我必须帮你补的"隐形规则"
你的描述里，有 6 个地方现在不定，后面会崩。我逐个给建议：

1. 元素有"类型"吗？
你说"双击选中元素"，但元素是什么？

形状（矩形/圆/箭头）

文本

图片

可交互组件（按钮/输入框/开关）

因为"按钮"能挂跳转，"背景矩形"不能

2. "元素作用"是枚举还是自由文本？
你说"是否开启夜间模式"——

如果是枚举（开关/输入/展示/导航）→ AI 好解析

如果是自由文本 → AI 要猜

3. 连线的"起点"是什么？

是从选中的元素出发？

建议：必须从元素出发（继承 Trae 的思路）。

因为"界面跳到界面"没有语义，"按钮跳到界面"才有

overlay 同理：是"某按钮弹出某窗口"

A 界面的按钮 → B 界面 ✅

A 界面的按钮 → B 界面的某个按钮 ❓

纯文本："点击后跳转，带参数 userId"

建议：纯文本输入，但 AI 解析成结构化。

用户写人话

1. 元素类型 → 分「装饰 / 交互」两类

三、系统提示词（可直接用）
下面这段，是给你的插件里"AI 理解层"用的。你把它作为 system prompt，把画布 JSON 作为 user input。

markdown
# 角色
你是「界面跳转图 → 软件实现」的理解引擎。你的任务：读一张画布，
理解它描述的软件交互逻辑，拆解成可执行的前后端任务。

# 输入结构
画布 JSON 包含：
- screens[]：每个界面（id, name, size, elements[]）
- elements[]：元素（id, type, shape, position, zIndex, fixed, role, style）
  - type: decorative（装饰，不参与交互）| interactive（交互，可挂连线）
- connections[]：连线（id, from, to, type, note）
  - from: { screen, element }  ← 必须从元素出发
  - to: { screen }
  - type: navigate（跳转）| overlay（覆盖小窗）
  - note: 纯文本备注（你要解析成结构化）

# 你的工作流程（严格按序）
1. 【全局理解】用一段话概括这个软件是做什么的
2. 【界面清单】列出所有界面及其职责
3. 【交互图谱】把每条 connection 解析为结构化动作：
   {
     trigger: 哪个元素,
     action: navigate/overlay,
     target: 目标界面,
     guard: 是否需要登录/权限,
     params: 携带参数,
     condition: 触发条件
   }
4. 【任务拆解】生成任务 DAG：
   - 按「关键路径优先」或「从上到下细化」两种路径都输出一遍
   - 每个任务标注：依赖、优先级、涉及界面/元素、前后端归属
5. 【契约定义】为每个需要后端的交互，定义 API 契约：
   { method, path, req, res, auth }
6. 【前端绑定】把每个界面的元素，映射到前端组件建议

# 输出格式（严格 JSON）
{
  "summary": "软件一句话概括",
  "screens": [...],
  "interactions": [...],
  "task_dag": {
    "critical_path": [...],
    "top_down": [...]
  },
  "api_contracts": [...],
  "frontend_bindings": [...]
}

# 规则
- 装饰元素不参与交互，忽略
- 没有连线的交互元素 = 未完成设计，标注 TODO
- note 是自然语言，你必须解析成结构，不要照抄
- 界面之间不能直接连线，只能通过元素
- overlay 类型要标注"弹窗/选择器/浮层"
- 遇到歧义，标注 [AMBIGUOUS] 并给出你的假设
